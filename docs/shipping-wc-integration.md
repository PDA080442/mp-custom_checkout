# Интеграция доставки: режимы и приёмка (§28.1)

**Статус:** спецификация по задаче `dp.md` §28.1 (Define Shipping Modes And Acceptance Criteria).  
**Связь с эпиком:** `dp.md` §28 — WC как источник правды для СДЭК / динамических тарифов.

**Аудит потока данных (§28.2):** см. отдельный файл [shipping-wc-data-flow-audit.md](./shipping-wc-data-flow-audit.md) — таблица событий AJAX, `shipping_price`, `suppress_shipping_in_summary`, валидация каталога vs WC.  
**Исходный промпт:** зафиксировать режимы `delivery.pricing_mode`, матрицу сценариев × режим и критерии приёмки на основе кода `CheckoutRouteContext`, `CheckoutAjaxHooks`, `checkout-frontend.js` (fulfillment / `date_conditions`).

Документ **не дублирует** полный эпик в `dp.md`; при расхождении приоритет у реализации в репозитории после merge соответствующих PR.

## 1. Бизнес-цель

**Целевое поведение «как на классическом WooCommerce checkout»** (эталон: стенд `/zakaz/` с методами вида `official_cdek:<instance_id>`):

- Суммы доставки **пересчитываются** при изменении адреса (город, индекс, страна/регион), потому что WooCommerce пересчитывает пакеты и rate’ы (в т.ч. плагином СДЭК).
- В итоге заказа до оплаты отображаются **согласованные** subtotal / shipping / discount / tax / total с тем, что реально будет в заказе WC.

**Текущее поведение модуля (база для сравнения):**

- Каталог `delivery.shipping_catalog` задаёт методы и **статические** цены в админке; фронт кладёт в `state.frontendStore.fulfillment.date` поля `shipping_method_id`, `shipping_method_title`, `shipping_price` (см. `checkout-frontend.js`, выбор доставки).
- `CheckoutRouteContext::get_cart_data()` при числовом `answers.date_conditions.shipping_price` **подменяет** отображаемую сумму доставки в `summary` этим значением (даже если в корзине WC другая сумма).
- Для сценария `pickup` и шагов `address_delivery` / `recipient` при `needs_shipping()` доставка в summary может **скрываться** (`shipping_deferred`, принудительно 0) — см. `suppress_shipping_in_summary` в `CheckoutRouteContext`.
- При включённом `checkout_ui_v2` валидация `shipping_method_id` идёт по **внутреннему каталогу** (`CheckoutAjaxHooks::validate_shipping_answers_payload` + `shipping_catalog()`), а не по rate’ам из `WC()->cart`.

Поле `delivery.wc_integration.respect_chosen_shipping_methods` хранится в настройках и нормализуется при сохранении; в админке есть подсказка по смыслу. На момент §28.3 рантайм-логика плагина **не** ветвится по этому флагу (пересчёт и выбор rate — стандартное поведение WooCommerce после `calculate_totals()`; диагностический лог расхождений см. `WcCustomerShippingSync`).

## 2. Режим настройки: `delivery.pricing_mode`

Один ключ в секции `delivery` (имя и вложенность уточняются при реализации в `SafeSettingsResolver`; ниже — каноническая семантика).

| Значение | Описание | Источник цены доставки в UI | Источник списка методов |
|----------|----------|-----------------------------|-------------------------|
| `catalog` | Текущее поведение (обратная совместимость). | `shipping_price` из ответов шага / каталога; при необходимости подмена в `get_cart_data()`. | `shipping_catalog` в настройках модуля. |
| `woocommerce` | Цель эпика §28. | После синка адреса с `WC()->customer` и пересчёта — **фактические** суммы из корзины WC (`get_shipping_total()` / пакеты); поле `shipping_price` из сессии **не** переопределяет итог. | Список rate’ов из `WC()->cart->get_shipping_packages()` (или эквивалент после `calculate_shipping()` / `calculate_totals()`). |
| `hybrid` | **Зарезервировано** (не в MVP §28). Возможные смыслы: каталог как «витрина», цена согласуется с WC; или часть методов из каталога, часть из WC. Требует отдельного ADR после пилота `woocommerce`. | TBD | TBD |

**Рекомендация по умолчанию для существующих прод-инсталляций:** `catalog`, пока не пройдены регрессы на стенде со СДЭК; затем переключение на `woocommerce` осознанно (см. `docs/postdeploy-smoke-checks.md` / внутренний релизный чеклист).

**Рекомендация для новых стендов под СДЭК:** после стабилизации §28.3–§28.5 — `woocommerce`.

## 3. Сценарии модуля (`mp-cc`) × режимы

Идентификаторы сценариев: `pickup`, `krasnoyarsk_delivery`, `other_city_delivery` (`ScenarioStepRegistry`).

### 3.1 Матрица «что показываем / когда блокируем Далее»

| Сценарий | Поля адреса (шаг 1) | `catalog` | `woocommerce` (целевое) |
|----------|---------------------|-------------|---------------------------|
| **pickup** | Скрыты (`hide_address_fields`), выбор точки самовывоза. | Доставка в summary обычно отложена / 0 до оплаты; метод `pickup` из каталога. «Далее» по правилам текущего шага (дата/условия и т.д.). | WC: обычно только **local_pickup** или аналог в зонах; пересчёт по ПВЗ магазина. Подмена `shipping_price` не нужна. Согласовать с §28.5: не ломать `shipping_deferred`, если это сознательный UX. |
| **krasnoyarsk_delivery** | Адрес доставки по Красноярску (город может быть зафиксирован логикой сценария). | Методы из каталога (напр. «доставка по Красноярску», курьер, ПВЗ) со **статическими** ценами. «Далее» без выбора `shipping_method_id` — ошибка валидации (см. `shipping_method_id` required). | Методы и цены из WC; при смене уточнений адреса — повторный пересчёт. Валидация: выбранный rate **существует** в пакетах. |
| **other_city_delivery** | Полный адрес (город, индекс, регион и т.д.). | Как сейчас: каталог + `shipping_price`. | Как классический `/zakaz/`: СДЭК курьер / СДЭК ПВЗ / Почта и др. из зон WC; **обязательна** синхронизация города в WC до расчёта (§28.3). |

### 3.2 ПВЗ СДЭК (карта, мета заказа)

| Релиз | Объём | Обоснование |
|-------|--------|-------------|
| **MVP (рекомендация §28.1)** | Сначала **курьерские** тарифы СДЭК (`official_cdek` до двери) + остальные flat/local методы WC. | Меньше связки с UI карты и session meta плагина СДЭК. |
| **Следующий инкремент** | Тарифы **до ПВЗ** + выбор точки как в нативном checkout. | Нужны поля/meta, которые плагин пишет при выборе ПВЗ; отдельная задача §28.6 / подэпик. |

До sign-off заказчика зафиксировать в тикете: **MVP без ПВЗ** или **с ПВЗ** — от этого зависит объём §28.4–§28.6.

**Реализация MP (ПВЗ + сессия + заказ):** пошаговый чеклист и контракт фронта (`window.mpCcSetCdekOfficeCode`, AJAX `cdek_set_office`) — в [cdek-mp-checkout-checklist.md](./cdek-mp-checkout-checklist.md).

## 4. Нефункциональные требования (черновик)

1. **Частота AJAX:** при вводе города/индекса не вызывать полный пересчёт WC на каждый символ; debounce на фронте (величина из существующих паттернов модуля или 300–500 ms).
2. **Ошибка СДЭК / таймаут:** не блокировать checkout бессрочно; показать понятное сообщение и предложить повтор / смену способа; логировать без PII (`mp_custom_checkout_log`).
3. **Согласованность итога:** при `woocommerce` итог в sidebar должен совпадать с `WC()->cart` после последнего успешного пересчёта (критерий регресса §28.5).
4. **Безопасность:** не логировать полный адрес и телефон в каналы, где это не оговорено политикой.

## 6. Черновик строк для QA-дока (вставить вручную в `cq.md` при готовности)

Шаблон для копирования:

1. **REG-SHIP-01** (`catalog`): смена города не меняет цену доставки, если в каталоге фиксированная цена.
2. **REG-SHIP-02** (`woocommerce`): смена города с A на B меняет cost у `official_cdek:*` так же, как на эталонной странице `/zakaz/`.
3. **REG-SHIP-03** (`woocommerce`): после F5 восстанавливается выбранный `shipping_method` (строка `method_id:instance_id`), итог не «мигает».
4. **REG-SHIP-04** (`pickup`): самовывоз не показывает лишнюю платную доставку в summary (согласно правилам `shipping_deferred`).
5. **REG-SHIP-05**: купон + пересчёт доставки не дают отрицательного total.
